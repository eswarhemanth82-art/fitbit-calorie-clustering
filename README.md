## Using the real dataset
The real `Fitbit_dataset.xlsx` has been used (`data/fitbit_dataset.csv`, 14,102 rows).
**Important**: the raw file had 3 extra engineered columns — `Base_MET`, `HR_Intensity`,
`Effective_MET` — that reconstruct `Calories_Burned` almost exactly
(`Effective_MET × Weight × Session_Duration = Calories_Burned`, corr = 0.9999996).
These were **dropped as target leakage** before training — a model given those columns
would trivially hit ~100% R² without learning anything real. Only the columns from the
original project schema were used as features.

## Results (on real data, post leakage removal)
- **Regression**: XGBoost best, R²=0.998, MAE=3.9, RMSE=6.5 (target R²≥0.80 ✅).
  Still very high because the underlying data was generated from a deterministic formula
  (BPM/weight/duration → calories) with little to no sensor noise — worth noting in your
  report that real wearable data would likely show more MAE due to sensor error.
- **Clustering**: KMeans k=2, Silhouette=0.298 (target ≥0.15 ✅, comfortably above).
  Clusters split cleanly along **Experience_Level** and **Fat_Percentage** — cluster 0 is
  beginner/intermediate with higher fat%, cluster 1 is intermediate/advanced with lower
  fat% and longer sessions. Workout_Type is nearly evenly spread across both clusters,
  confirming the pattern found is behavioral/physiological, not just "workout type in disguise."

## Notes for the project report
- Outlier handling uses IQR capping (winsorizing), not row deletion, to preserve sample size.
- Clustering deliberately excludes Age/Height/Weight/Gender — physiologically these
  describe *who* someone is, not *how* they train, and including them diluted the
  intensity signal (silhouette dropped from 0.15 to ~0.12 when included — worth
  mentioning in your EDA/feature-selection writeup).
- PCA kept components explaining 90% variance rather than a fixed n_components,
  a defensible choice to justify in your report.
